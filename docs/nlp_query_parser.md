# 자연어 쿼리(LLM 기반) 파서 개발 — 추가 스코프

> 작성자: 김하영(인턴) · 원본: [인수인계_상세본.md](../handOver/인수인계_상세본.md) "9. 자연어 쿼리(LLM 기반) 파서 개발" (2026-08-21 분리)

이번 스코프(인수인계_상세본.md 1~8번 섹션)와 별개로, 태그 기반 파이프라인이 완성된 이후 잔여 기간에 자연어 검색
프로토타입을 추가로 진행하여 실제 검색 UI에 통합까지 완료했습니다. 상세 개발 기록은 Confluence
[Query Parsing] 문서에 있으며, 여기서는 다음 담당자가 알아야 할 핵심만 요약합니다.

### 9-1. 배경 및 목표

기존 태그 클릭 방식 검색과 별개로, "야간 우천 시 보행자 횡단 장면"처럼 자연어 문장을 입력하면
자동으로 검색 필터(구조화 쿼리)로 변환해주는 기능. 원래 계획(인수인계_상세본.md 5-2 참조)에서는 "다음 단계"로만
남겨뒀으나, 회사에 계약된 LLM API가 없는 상태에서 팀원(시은)이 개인 GPU 서버에 vLLM을 띄워둔
것을 확인하여 **무료로 프로토타입 검증까지 진행**했습니다.

### 9-2. 아키텍처

> ⚠️ 아래 아키텍처는 **시은 개인 GPU 서버**에 의존하는 현재 구조입니다. 시은도 인턴이며
> Motional 데이터/vLLM 서버 담당을 다른 사람에게 인수인계할 예정이나 후임자는 아직
> 미정입니다(문서 작성 시점 기준). 자세한 내용은 [인수인계_상세본.md](../handOver/인수인계_상세본.md) 0-1 섹션 경고 참고.

```
[유저] → index.html "AI 자연어 검색" 패널 (체크박스 필터와 완전 별개 UI/상태)
        → POST /api/nlquery (server.py)
        → SSH 터널(127.0.0.1:8001) → vLLM(Qwen3-14B-FP8, 시은 개인 GPU)
        → 구조화 쿼리(중첩 AND/OR) 반환
        → server.py가 그대로 검색 결과 리턴 X, index.html의 JS가 이 쿼리를
          Elasticsearch bool 쿼리로 변환(buildESQueryFromParsed()) → /api/search 재사용
        → 결과를 기존 카드 UI(renderResults())로 표시
```

- **체크박스와 완전 분리 설계**: 초기엔 파싱 결과를 체크박스 상태에 자동 반영(체크)하는 방식도
  검토했으나, taskName(AAA1/LSD) 자동 전환 필요성과 "필드 간 OR"(예: "밤이거나 비 오는")을
  체크박스로 표현할 방법이 없다는 문제로 인해 **완전히 독립된 검색 경로**로 단순화함. 자연어
  검색은 체크박스를 전혀 건드리지 않고, 곧바로 ES 쿼리로 변환해 결과만 보여줌.
- **vLLM 접속**: SSH 포트포워딩(`ssh -L 8001:127.0.0.1:8001 stradvision@10.50.10.181`)
  필요. `ui/.env`의 `VLLM_BASE_URL`이 이 로컬 포트를 가리킴. **vLLM은 systemd 미등록** — 인수인계_상세본.md 3-4
  섹션 참조. **이건 현재의 임시 구조를 설명한 것일 뿐, 신규 환경 구축 가이드는
  [인수인계_자격증명관리.md](../handOver/인수인계_자격증명관리.md) 5번 참조.**

### 9-3. 개발 과정 핵심 요약 (v1 → v20)

- **v1~v2**: 프롬프트에 규칙 텍스트만 추가하는 방식은 거의 효과 없음을 확인
- **v3**: few-shot 예시 + 출력 구조 변경(딕셔너리→조건 리스트)으로 정확도 급상승
- **임베딩 유사도 매칭 실험**(별도): `multilingual-e5-small`로 필드 설명 임베딩 매칭도 시도했으나,
  "야간에 소가 ego 차량 앞으로 지나가는 시나리오" 같은 복합 개념 쿼리에서 정답 필드가 78개 중
  65위로 밀리는 등 정확도가 낮아 **채택하지 않음** (동의어 보완용 fallback 정도로만 잠재 활용 가치)
- **v9**: taxonomy를 "형제 필드 그룹"(예: `behind_bike`/`behind_motorcycle`/`behind_long_vehicle`
  처럼 entity만 다른 필드들을 그룹으로 명시)으로 구조화 → few-shot 예시에 없던 새 조합에도 정확히
  일반화되는 것을 확인 (단, held-out 테스트에서 "동의어 표현"까지는 일반화가 불완전함을 나중에
  재확인, 9-4 참조)
- **v10**: LLM이 존재하지 않는 필드명을 지어내는 hallucination 문제 발견 → 프롬프트 규칙 +
  **코드단 검증 함수(`validate_and_sanitize()`)로 이중 방어**. 이 접근(확정적 문제는 코드로
  보장)이 이후 v18에서 다시 한번 핵심 해법으로 재사용됨.
- **v11~v14**: 속도/방향 축 동시 처리(예: "고속으로 좌회전"), LSD 태깅 자체가 야간 전용
  데이터라는 도메인 지식을 반영한 night 자동 추론, 부정 표현 중복 처리 정리, 자동 추론된
  조건에 "LSD 특성상 자동 추가" UI 배지를 붙여 투명성 확보(`auto` 플래그)
- **v15~v18**: v14의 night 자동 추론 규칙이 LSD 11개 필드 중 일부에서만 불안정하게 동작하는
  문제 발견. 원인으로 "lost in the middle"(긴 프롬프트에서 중간 내용에 대한 모델 attention
  저하) 가설을 세우고 검증했으나 부분 효과만 확인. **최종적으로 "이 규칙은 모델의 판단이
  아니라 100% 확정적인 도메인 규칙"이라는 점을 재인식하고, 프롬프트 튜닝 대신 후처리 코드
  함수(`enforce_lsd_implies_night()`)로 전환** — LSD 11개 필드 전수 테스트 100% 통과 확인.
  이어서 vLLM이 서빙하는 모델 자체를 Qwen3-VL-8B-Instruct에서 Qwen3-14B-FP8로 교체함
  (VRAM 효율 개선 + 정확도 향상 목적). 교체 과정에서 당시 시스템 프롬프트 토큰 수
  (8,278)가 그 시점 vLLM 컨텍스트 한도(8,192)를 초과하는 문제를 발견해, taxonomy 설명
  압축·중복 규칙 제거·예시 문구 압축으로 5,498토큰까지 줄였음(이후 vLLM 컨텍스트 한도
  자체도 39,168로 넉넉히 확장됨). 이 압축·모델 교체 과정에서 새로운 hallucination
  패턴 두 가지를 발견함: (1) 문장이 언급하지 않은 context 필드를 LLM이 임의로 채워
  넣는 것(B-1), (2) night 동의어 표현(밤길/야밤/한밤중 등)을 auto 플래그 판단에서
  놓치는 것(B-2). 비교 실험으로 원인을 분리해본 결과 — 압축 이전 원본 프롬프트를
  그대로 새 모델에 돌려도 같은 hallucination이 재현되어, 이 문제가 프롬프트 압축이
  아니라 모델 자체(또는 모델과 thinking-mode-off 조합) 특성에 가깝다는 것을 확인함
  (오히려 압축판이 전반적으로 더 나은 결과를 보임). 이 결과로 이번 버전을 **v19**(프롬프트
  압축)로, 이어서 B-1을 수정한 버전을 **v20**으로 명명함. B-1(임의 context 채우기)은
  실패 문장을 그대로 few-shot 대조쌍으로 추가하는 방식으로 개선해 실서비스에 반영
  완료(9-4 참조). B-2(auto 플래그 오분류)는 검색 결과 자체(필드 값)에는 영향이 없고
  UI 배지 표시만 부정확한 사소한 이슈로 확인되어, 우선순위를 낮춰 후속 과제로 남김
  (9-5 참조).

### 9-4. 정확도 및 일반화 평가 (중요 — 반드시 읽어야 함)

- 개발 과정에서 만든 테스트 문장 기준으로는 대부분 버전이 높은 정확도를 보였으나, **개발자가
  직접 만든 예시로 검증한 수치는 진짜 일반화 성능이 아닐 수 있다는 문제의식**으로 v13 기준
  **완전히 새로운 문장 20개(held-out 테스트)**를 별도로 진행함.
- **결과: 20개 중 75% 완전정답.** 특히 "오토바이 여러 대 근처에" vs "오토바이 여러 대에
  둘러싸인"처럼 **같은 의미의 다른 표현(동의어)에 대한 일반화가 아직 불완전**하다는 구체적
  반례를 확보함. 복잡한 중첩 문장 안에서 개별 조건의 정밀도가 떨어지는 경향도 확인됨.
- **프롬프트 압축(v19) + 모델 교체(Qwen3-14B-FP8) 이후 재검증**: 총 32문항(일반 15 +
  hallucination(B-1) 재현 표적 10 + auto 플래그(B-2) 표적 7)으로 다시 검증함. 일반
  15문항은 기존 held-out 문장과 겹치는 회귀 확인용 표본이라 순수 held-out 성격은 아니며,
  회귀 없이 정상 동작함을 확인하는 용도로 사용함(구체적 정답률 수치는 별도로 집계하지
  않음). held-out 성격이 더 강한 표적 문항 기준으로는 다음을 확인함:
  - **B-1(임의 context 채우기) 발생률**: 개선 전 30-40%(10문항 중 3-4건) → few-shot
    대조쌍 추가 후 0-10%(10문항 중 0-1건)로 크게 개선.
  - **B-2(auto 플래그 오분류) 발생률**: 여전히 약 43%(7문항 중 3건) 수준으로 미해결.
    다만 검색 결과 자체(필드 값)에는 영향이 없고 UI 배지 표시만 부정확한 사소한 이슈로
    확인되어 심각도는 낮음.
  - **동의어 일반화**: v13에서 발견됐던 "오토바이 여러 대에 둘러싸인" 케이스는 v19, v20
    양쪽에서 모두 정상 처리되는 것을 확인함 — 모델 크기를 8B에서 14B로 올린 것이 이
    문제에 실질적으로 도움이 됐다는 근거로 기록.
- **결론**: 지금 상태로도 실사용 가능한 수준이나, "100% 정확하다"고 오해하면 안 됨. 검수
  단계(review.html)에서 사람이 최종 확인하는 기존 워크플로우가 이 부정확성에 대한 안전장치
  역할을 함.

### 9-5. 다음 담당자가 이어받을 작업 (자연어 쿼리 관련, 우선순위 순)

1. **동의어 표현 일반화 개선** — 9-4에서 확인된 한계였으나, 모델을 Qwen3-14B-FP8로
   교체한 이후 재검증에서 부분 개선됨(v13 반례였던 "오토바이 여러 대에 둘러싸인" 케이스
   정상 처리 확인). 다만 지금까지의 재검증은 팀원 본인이 작성한 표적 문항 위주라, 우선순위를
   낮추되 아래 2번의 blind 검증으로 재확인이 필요함
2. **Blind held-out 테스트** — 프롬프트 내용을 모르는 다른 팀원이 직접 작성한
   문장으로 진짜 일반화 성능을 재측정 (지금까지의 문항은 모두 본인이 작성해 편향 가능성 있음)
3. **auto 플래그 오분류(B-2, night 동의어 인식 부족) 정리** — 우선순위 낮음. 검색 결과
   자체(필드 값)에는 영향 없고 UI 배지 표시만 부정확한 이슈(9-4 참조)
4. **vLLM 운영 안정화** — 현재 systemd 미등록, 시은 개인 서버 의존. 예고 없이 꺼진 전례
   있음(인수인계_상세본.md 3-4 섹션 참조). ⚠️ 담당자 관련 주의사항은 인수인계_상세본.md 0-1 섹션 경고 참고.
   **[인수인계_자격증명관리.md](../handOver/인수인계_자격증명관리.md) 5번의 신규 환경 구축 가이드를 참고해 이전을 최우선으로
   진행할 것을 권장. 아울러 현재 vLLM 컨텍스트 한도가 39,168로 넉넉하게 확장되어 있는데,
   이는 프롬프트 압축 이전(8,192 초과 문제) 대응 과정에서 임시로 크게 늘려둔 값이므로,
   실서비스가 안정화된 이후에는 다른 사람과 공유하는 GPU 자원을 덜 점유하도록 적정 수준
   (예: 12,000~16,000)으로 다시 낮추는 것을 권장**
5. **`low_streetlight_road` 필드의 auto 플래그(UI 배지) 표시 미세 오차** — 검색 결과 자체엔
   영향 없는 사소한 잔여 이슈, 우선순위 낮음
6. **복잡한 중첩 문장에서의 개별 조건 정밀도 점검 체계** — 9-4에서 확인된 패턴을 팀에 공유하고,
   복잡한 질의 결과는 검수 단계에서 한 번 더 확인하는 습관 안내 필요
