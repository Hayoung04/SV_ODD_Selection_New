## 1. 프로젝트 개요

### 1-1. 목표

엔지니어가 비정형 요구사항에서 의미 있는 주행 데이터를 수동으로 찾고, 화면으로 눈으로 확인하며 선택하던 과정을 자동화·시스템화한다.

- **현재 스코프(달성된 목표)**: ODD(Operational Design Domain) 태깅 데이터 + Motional 시나리오 데이터를 **태그 기반으로 통합 검색**하고, 그 결과를 **실제로 실행(CSV 추출, 검수 UI에서 Accept/Reject 판정)까지** 하는 것. 즉 "검색만 되는 것"이 아니라 "태그를 클릭 → 프레임 목록 즉시 조회 → CSV로 다른 시스템에 바로 연동하거나 검수 UI로 최종 승인/반려까지 처리"하는 end-to-end 파이프라인을 완성하는 것이 이번 스코프의 목표였음.
- **스코프 확정 배경**: 최초에는 "자연어 쿼리 → ODD 기반 데이터 경로 반환"이라는 개념으로 시작했고, 이후 "정책 기반 구조 + Kafka 스트리밍 + IP 보호까지 고려한 SaaS급 아키텍처"로 요구가 확장된 시점이 있었음. 하지만 인턴 잔여 기간(3주)을 감안해 **"단순화된 파이프라인(파일/태그 검색 수준)"으로 스코프를 현실화**하기로 결정, 8/5부터 이 기준으로 구현 착수함 .
- **자연어 쿼리(LLM 기반) 기능은 원래 이번 스코프에 포함되지 않았으나, 태그 기반 파이프라인 완성 이후 잔여 기간에 프로토타입까지 추가로 진행하여 실제 검색 UI에 통합 완료함** — 상세 내용은 [docs/nlp_query_parser.md](../docs/nlp_query_parser.md) 참조.

### 1-2. 로드맵 (Step 1~5)

1. **Step 1**: Docker 기반 로컬 검색 엔진(Elasticsearch + Kibana) 환경 구축
2. **Step 2**: 초기 데이터 연동 (Polling 방식 → 이후 Kafka로 전환)
3. **Step 3**: 인덱싱 및 검색 기능 검증
4. **Step 4**: 데이터 파이프라인 고도화 (Kafka/MSK 연동)
5. **Step 5**: 시각화 및 UI/서버화 (검색 UI, 검수 UI)
6. **(추가) 자연어 쿼리 파서**: Step 5 완료 후 잔여 기간에 진행한 추가 작업. [docs/nlp_query_parser.md](../docs/nlp_query_parser.md) 참조.

## 2. 시스템 아키텍처

### 2-1. 전체 데이터 흐름 (현재 상태 기준)

```
[Qumulo (AAA1/LSD 10fps + Motional)]
        │  (지금은 수동 업로드/테스트 경로, 향후 실제 자동 적재 경로 연결 예정)
        ▼
[dev.shared.odd-tagging.input] (Kafka/MSK 토픽, 파티션 3개)
   ├─ ODD 서비스(호연)가 같은 토픽을 다른 Consumer Group으로 구독 (실제 태깅 수행)
   └─ index 서비스(우리) — group: odd-selection-consumer
        ▼
[kafka_consumer.py] (systemd: odd-kafka-consumer, 상시 구동)
   └─ kafka_message_handler.py 가 unified_pipeline.py의 함수들을 재사용
        ├─ 10fps → 1fps 다운샘플링 (정수초별 최근접 프레임 선택)
        ├─ Motional 이벤트 매칭 (±0.5초)
        └─ Bulk API로 Elasticsearch 색인
        ▼
[Elasticsearch: odd-frames-v2] (현재 976건, AAA1 488 + LSD 488)
        ▼
[검색 UI: index.html] ← server.py (systemd: odd-search-ui, 상시 구동)
        │        ├─ 체크박스 필터 검색 (기본 경로)
        │        └─ AI 자연어 검색 (/api/nlquery, 체크박스와 완전 별개 경로 — docs/nlp_query_parser.md 참조)
        ▼
[검수 UI: review.html] — 씬 전체 재생 + 기본 Accept/예외만 Reject 워크플로우
```

**참고**: Motional 데이터는 `motional_producer.py`가 Cron(10분 주기)으로 로컬 파일을 스캔해 같은 `odd-tagging.input` 토픽에 발행 → Consumer가 처리. ODD 서비스는 자신이 발급한 jobId와 일치하는 메시지만 처리하므로, `motional-verify-{n}` 접두사를 쓰면 우리 메시지를 무시하고 안전하게 공존 가능(호연 확인 완료).

### 2-2. 핵심 설계 결정 및 이유

| 결정                                                    | 이유                                                                                                                                                                              |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ODD/Motional 통합 인덱스 (경로가 키, 태그는 필드)       | Meeting #3에서 확정된 원칙                                                                                                                                                        |
| 1fps 다운샘플링 (원본은 10fps)                          | 회사 정책. 초기엔 "10fps가 맞다"고 판단했다가, 실제로는 "촬영/태깅은 10fps, 최종 사용은 1fps"가 정책임을 재확인해 재설계함                                                        |
| ODD 샘플에 ±0.5초 담당 구간 배정                        | 1초 간격 샘플링에 정확히 절반씩 배정하면 빈틈없이 이어붙어, 어떤 시각의 Motional 이벤트든 반드시 매칭됨. 판정 기준은 "조금이라도 겹치면 매칭"(관대한 기준, 놓치지 않는 것이 우선) |

| doc_id = `task-recording-정수초`                        | 같은 정수초에 10fps 프레임 여러 개가 후보로 들어와도, 오차가 가장 작은 것으로 자동 덮어써 1개만 남도록 설계                                                                       |
| unified ODD+Motional 검색 엔진 먼저 시도, 안 되면 분리  | Meeting #1/2에서 합의된 순서                                                                                                                                                      |
| 자연어 쿼리를 체크박스 필터와 완전히 분리된 경로로 설계 | 초기엔 파싱 결과를 체크박스 상태에 자동 반영하는 방식을 검토했으나, taskName(AAA1/LSD) 자동 전환·필드 간 OR 조건을 체크박스로 표현 불가 등 매핑 문제가 많아 단순화. [docs/nlp_query_parser.md](../docs/nlp_query_parser.md) 9-2 참조      |

### 2-3. ODD vs Motional 데이터 구조 차이

- **ODD (AAA1, LSD, LD_General, OD_General)**: taskName별로 다른 속성 스키마, 값은 `present`/`absent`/`unknown` 3단계. AAA1은 19개 속성 + weather/time/road_type 등 촬영조건 필드 보유, LSD는 11개 속성(전부 야간 전용, 촬영조건 없음).
- **Motional**: 58개 시나리오, boolean이 아니라 실제로는 **start/end 구간(interval)** 정보로 전달됨 → 프레임 단위로 매핑. 5개 카테고리로 그룹핑됨.
- **LD_General/OD_General**: **현재도 필드 값 방식(present/absent/unknown 여부)과 실제 출력 예시가 미확인 상태**이며 **다음 담당자가 반드시 확인해야 할 항목.**

- 구독 토픽: `dev.shared.odd-tagging.input` (파티션 3개, 현재 총 1210건 — 테스트 데이터 포함)

- Consumer Group: `odd-selection-consumer` (우리 그룹, Lag 0/STABLE 확인됨). ODD 서비스는 별도 그룹으로 같은 토픽을 구독 — **토픽은 안 나뉘고 Consumer Group으로만 구분됨**
- 자격증명: `~/.aws/credentials` (profile: `odd-msk`, `odd-indexer`), `~/.aws/config` (region: `ap-northeast-2`) — 프로젝트 폴더 밖(홈 디렉토리)에 격리 저장
- Kafka UI(kafbat) 접근 절차는 [인수인계_자격증명관리.md](./인수인계_자격증명관리.md) 4-4 참고 (조회 전용 계정,
  토픽 생성/삭제 불가, VPN 불필요)

### 3-4. systemd 서비스 목록

| 서비스명             | 역할                                   | 상태                                                                                                                        |
| -------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `odd-polling`        | 구 폴링 방식 (파일 스캔)               | **중단됨 (stop+disable)**, Kafka로 완전 전환됨. 코드(`unified_pipeline.py`)는 Kafka 경로가 재사용 중이라 삭제하지 않고 유지 |
| `odd-kafka-consumer` | Kafka 메시지 실시간 수신 → ES 색인     | 상시 구동 중                                                                                                                |
| `odd-search-ui`      | 검색/검수 UI 백엔드 서버 (`server.py`) | 상시 구동 중 (ThreadingTCPServer로 동시 요청 처리 가능하도록 수정됨)                                                        |

Cron 등록: `motional_producer.py`가 10분마다 신규 Motional 파일 스캔 → 발행 (`crontab -l`로 확인)

**참고 — vLLM은 systemd 미등록**: 자연어 쿼리 파서가 호출하는 vLLM([docs/nlp_query_parser.md](../docs/nlp_query_parser.md) 9-2 참조)은 `odd-search-ui`와 달리 systemd로 관리되지 않으며, 시은 개인 서버에서 임시로 실행 중. 예고 없이 중단될 수 있음(실제 개발 중 1회 발생) — **다음 담당자는 [인수인계_자격증명관리.md](./인수인계_자격증명관리.md) 5번의 신규 환경 구축 가이드를 참고해 별도 환경으로 이전을 검토해야 함**([docs/nlp_query_parser.md](../docs/nlp_query_parser.md) 9-5 참조).

운영 명령 공통 패턴:

```
sudo systemctl status <서비스명>
sudo journalctl -u <서비스명> -f
sudo systemctl restart <서비스명>
```

※ Python 스크립트를 systemd로 돌릴 때는 반드시 `ExecStart`에 `-u`(unbuffered) 옵션 추가 — 안 하면 `journalctl` 로그가 안 보임 (Step 2, Step 4에서 각각 한 번씩 겪은 이슈).

## 5. 다음 담당자가 이어받아야 할 작업

### 5-1. 우선순위 높음

1. **ODD `output` 토픽 실데이터 유입 대기 중 (현재 0건)** — 호연 측 ODD 서비스 V2(HTTP 콜백 → Kafka produce/consume 전환) 완성 대기 상태. 실데이터 도착 시:
   - `kafka_message_handler.py`의 `extract_message_type()`, `extract_odd_fields()`, `extract_motional_fields()` 3개 함수를 **실제 메시지 스키마에 맞춰 재작성 필요** (현재는 추정 로직)
   - 도착 즉시 `audit_pipeline.py`로 정식 전수 감사 실시 (아직 미실시)
2. **LD_General/OD_General 스키마 미확정** — present/absent/unknown 방식인지, taskName 문자열이 정확한지 ODD 태깅 서비스 담당자에게 확인 필요 (문서 작성 시점엔 호연이 담당이었으나, 인턴 특성상 바뀔 수 있음).

### 5-2. 후속 계획 (이번 스코프에는 포함되지 않았던 것)

발표 자료 기준 향후 계획 3가지:

1. **ODD Service V2 완료 후 실데이터 연동** — HTTP→Kafka 전환 완료 시 output 토픽 실데이터로 전체 파이프라인 재검증 (5-1의 1번과 동일 항목)
2. **유저테스트** — Motional 검수 로직 및 전체 플로우를 유저테스트 후 재반영
3. **LLM/MCP 기반 자연어 쿼리** — ~~아직 검토 단계이며 설계도 확정 전~~ **→ 인턴 기간 중 프로토타입 완성 및 실제 UI 통합까지 완료됨 (v1~v20). 상세 내용, 성능 검증 결과, 남은 작업은 [docs/nlp_query_parser.md](../docs/nlp_query_parser.md) 참조.** 참고로 실제 구현해본 결과, "RAG"보다는 "LLM 기반 쿼리 파싱(text-to-SQL 유사) + 결정론적 코드 후처리"에 가까운 형태로 귀결됨 — ODD/Motional 태그가 둘 다 구조화된 라벨 카탈로그이기 때문에 formal 필터가 주 검색 수단이 되는 것으로 확인됨. 임베딩 유사도 검색은 자체 실험 결과 복합 개념 쿼리에서 부정확하여([docs/nlp_query_parser.md](../docs/nlp_query_parser.md) 9-3 참조) 채택하지 않음.

- **통합 ODD+Motional 메타데이터 DB**: PostgreSQL + pgvector — 실제 구현 결과 Elasticsearch만으로 자연어 쿼리까지 충분히 처리 가능함을 확인했으므로, 현재로선 우선순위 낮음 ([docs/nlp_query_parser.md](../docs/nlp_query_parser.md) 참조)

### 5-3. 우선순위 낮음 / 후순위

### 5-4. (참고) Motional 구간 검수 UI 아이디어 — 개인 실험, 미승인

review.html의 "씬 전체 재생 + 기본 Accept + 예외만 Reject" 철학을 Motional 이벤트에도
동일하게 적용해볼 수 있다는 아이디어를 인턴십 마지막에 개인적으로 프로토타입해봄
(팀 요구사항 아니었고 승인도 받지 않은 상태 — 아래 5-1/5-2/5-3과 달리 "해야 할 작업"이
아니라 참고용 메모임).

- **문제의식**: 기존 review.html은 프레임 하나하나를 기준으로 검수해야 해서, (1) 검수 자체가
  번거로웠고, (2) 지금 보고 있는 프레임에 어떤 ODD/Motional 태깅 정보가 걸려있는지 한눈에
  파악하기 어려웠음. 특히 Motional은 원래 시간 구간(start~end) 단위 데이터인데 이걸 프레임
  단위로 쪼개서 한 프레임씩 검수하다 보니 비효율적이었음. 여기에 더해, ODD 프레임 검수(빠른
  기본-accept 방식)와 Motional 이벤트 검수(느린 명시적 판정 방식)가 서로 다른 페이지/철학으로
  분리돼 있는 것도 비효율을 키우는 요인이었음
- **시도한 방향**: 씬을 한 번 재생하면서, 재생헤드가 지나가는 순간 활성화된 ODD 속성 +
  Motional 이벤트 태그만 화면에 보여주고, 이상한 태그만 개별로 flag(=reject)하는 방식.
  태그 개수가 많아도 한 번에 다 보려 하지 않고 "지금 이 순간 것만" 판단하게 해서 인지
  부하를 줄이는 게 핵심 아이디어
- **상태**: 더미 데이터로 만든 로컬 HTML 프로토타입 (`odd_motional_unified_review_demo.html`).
  레포·GitHub에는 올리지 않았고, 팀 검토·승인도 받지 않은 개인 실험 파일임
- **파일**: 이 문서엔 첨부하지 않음 — 하영이 퇴사 전 다음 담당자에게 별도로 직접 전달 예정
  (브라우저에서 파일 하나만 열면 바로 동작하는 단일 HTML, 서버/설치 불필요)
