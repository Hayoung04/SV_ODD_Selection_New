> 작성자: 김하영(인턴) · 작성일: 2026-08-14 (자연어 쿼리 섹션 추가: 2026-08-19)
> 프로젝트: Query-based SV Data Selection with ODD (Motional 협업 프로젝트)

## 0. 용어 사전

이 프로젝트를 처음 보시는 분을 위한 최소 용어 정리입니다. 아래 내용을 모르면 이후 섹션이 잘 안 읽힐 수 있어 맨 앞에 둡니다.

| 용어                              | 설명                                                                                                                                                                                                              |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ODD**                           | Operational Design Domain(운행 설계 영역). 자율주행 시스템이 정상 동작하도록 설계된 조건 범위(날씨, 도로 유형, 시간대 등)를 뜻함. 이 프로젝트에서는 "프레임 하나하나에 붙는 상황 태그"를 가리키는 말로도 쓰임     |
| **Motional**                      | "주행 시나리오 이벤트" 데이터(예: 좌회전 시작, 보행자 근접 등)를 가리킴. ODD와 별개 축의 데이터로, 시간 구간(start~end) 형태로 옴                                                                                 |
| **AAA1 / LSD**                    | ODD 태깅 작업의 종류(taskName) 이름. AAA1은 19개 속성(날씨/도로유형/특정 객체 등), LSD는 11개 속성(전부 야간 전용, 광원/반사 관련)을 담당. `LD_General`/`OD_General`이라는 taskName도 있으나 스키마가 아직 미확정 |
| **present / absent / unknown**    | ODD 태그 값의 3단계. "그 속성이 있음 / 없음 / 판단불가"                                                                                                                                                           |
| **taskName**                      | 태깅 작업의 종류를 구분하는 값(AAA1, LSD 등). taskName마다 속성 스키마(어떤 필드가 있는지)가 다름                                                                                                                 |
| **Qumulo**                        | 회사의 원본 데이터가 저장된 네트워크 스토리지(NAS). 서버에 마운트해서 사용                                                                                                                                        |
| **Kafka / MSK**                   | 실시간 메시지 큐 시스템. AWS MSK는 그 관리형(Managed) 버전. "데이터가 생성되는 곳"과 "데이터를 쓰는 곳" 사이에서 메시지를 전달하는 역할                                                                           |
| **토픽 (Topic)**                  | Kafka에서 메시지가 쌓이는 "채널" 하나. 이 프로젝트는 `dev.shared.odd-tagging.input` 토픽 하나를 여러 서비스가 함께 구독함                                                                                         |
| **Consumer Group**                | 같은 토픽을 읽는 "읽음 위치"를 독립적으로 관리하는 단위. 우리 그룹(`odd-selection-consumer`)과 ODD 서비스 그룹은 서로 영향을 주지 않고 각자 처음부터 끝까지 읽을 수 있음                                          |
| **IAM / OAUTHBEARER**             | AWS의 계정 인증 방식(IAM)과, Kafka Python 클라이언트가 그 인증을 구현하는 방식(OAUTHBEARER)                                                                                                                       |
| **Elasticsearch / Kibana**        | 검색엔진(Elasticsearch)과 그걸 웹 화면으로 보는 도구(Kibana). Docker로 로컬에 띄워서 사용 중                                                                                                                      |
| **인덱스 (Index)**                | Elasticsearch에서 데이터를 저장하는 단위. 이 프로젝트의 핵심 인덱스는 `odd-frames-v2`(프레임 데이터), `odd-reviews`(검수 결과)                                                                                    |
| **1fps 다운샘플링**               | 원본은 초당 10장(10fps)으로 촬영되지만, 회사 정책상 최종적으로는 "1초에 1장"만 골라 사용함. 그 변환 과정                                                                                                          |
| **tiling (±0.5초 매칭)**          | 1fps로 골라낸 각 프레임에 앞뒤 0.5초씩(총 1초) 담당 구간을 배정해서, 그 구간과 겹치는 Motional 이벤트를 매칭하는 방식                                                                                             |
| **doc_id**                        | Elasticsearch에 저장되는 문서 하나의 고유 ID. `taskName-recording_id-정수초` 형식으로 고정해서, 같은 자리에 더 정확한 프레임이 나중에 오면 자동으로 덮어써짐                                                      |
| **systemd 서비스**                | 서버가 백그라운드에서 프로그램을 상시 실행/자동 재시작하게 해주는 리눅스 기능. 이 프로젝트는 `odd-kafka-consumer`, `odd-search-ui` 두 개를 이 방식으로 상시 구동 중                                               |
| **Bulk API**                      | Elasticsearch에 문서를 한 건씩이 아니라 여러 건을 묶어서 한 번에 저장하는 방법. 속도 개선을 위해 도입됨                                                                                                           |
| **전수 감사 (audit_pipeline.py)** | 원본 파일을 다시 읽어 "정답"을 독립적으로 계산한 뒤, 실제 Elasticsearch에 저장된 값과 하나하나 대조하는 검증 스크립트. 데이터가 늘어날 때마다 재실행하는 표준 절차                                                |
| **review.html (검수 UI)**         | 프레임을 눈으로 보면서 Accept(맞음)/Reject(틀림)/Pending(보류)를 판정하는 화면. 판정 결과는 `odd-reviews` 인덱스에 저장됨                                                                                         |
| **vLLM**                          | 오픈소스 모델(여기서는 Qwen3-VL-8B-Instruct)을 OpenAI API와 호환되는 형태로 자체 호스팅해주는 서빙 프레임워크. 팀원(시은) 개인 GPU 서버에서 실행 중이며, API 비용 없이 무료로 활용                                |
| **taxonomy**                      | 이 문서에서는 "LLM에게 알려주는 필드 목록 + 각 필드의 뜻풀이"를 가리키는 말로 사용. 자연어 쿼리 파서가 문장을 어떤 필드로 매핑할지 판단하는 기준이 되는 참조 자료                                                 |
| **few-shot 예시**                 | 프롬프트 안에 "이런 입력엔 이렇게 답해라"는 예시 몇 개를 직접 넣어서 LLM의 응답 패턴을 유도하는 기법. 모델 가중치를 바꾸는 학습(fine-tuning)이 아니라, 매 요청마다 프롬프트에 새로 포함되는 방식                  |
| **held-out 테스트**               | 프롬프트 개발에 전혀 쓰지 않은 새로운 문장으로 정확도를 검증하는 것. 개발 중 썼던 예시와 겹치는 문장으로 검증하면 "암기"인지 "진짜 이해"인지 구분이 안 되므로, 진짜 일반화 성능을 보려면 반드시 필요              |

## 1. 프로젝트 개요

### 1-1. 목표

엔지니어가 비정형 요구사항에서 의미 있는 주행 데이터를 수동으로 찾고, 화면으로 눈으로 확인하며 선택하던 과정을 자동화·시스템화한다.

- **현재 스코프(달성된 목표)**: ODD(Operational Design Domain) 태깅 데이터 + Motional 시나리오 데이터를 **태그 기반으로 통합 검색**하고, 그 결과를 **실제로 실행(CSV 추출, 검수 UI에서 Accept/Reject 판정)까지** 하는 것. 즉 "검색만 되는 것"이 아니라 "태그를 클릭 → 프레임 목록 즉시 조회 → CSV로 다른 시스템에 바로 연동하거나 검수 UI로 최종 승인/반려까지 처리"하는 end-to-end 파이프라인을 완성하는 것이 이번 스코프의 목표였음.
- **스코프 확정 배경**: 최초에는 "자연어 쿼리 → ODD 기반 데이터 경로 반환"이라는 개념으로 시작했고, 이후 "정책 기반 구조 + Kafka 스트리밍 + IP 보호까지 고려한 SaaS급 아키텍처"로 요구가 확장된 시점이 있었음. 하지만 인턴 잔여 기간(3주)을 감안해 **"단순화된 파이프라인(파일/태그 검색 수준)"으로 스코프를 현실화**하기로 결정, 8/5부터 이 기준으로 구현 착수함 .
- **자연어 쿼리(LLM 기반) 기능은 원래 이번 스코프에 포함되지 않았으나, 태그 기반 파이프라인 완성 이후 잔여 기간에 프로토타입까지 추가로 진행하여 실제 검색 UI에 통합 완료함** — 상세 내용은 9번 섹션 참조.

### 1-2. 로드맵 (Step 1~5)

1. **Step 1**: Docker 기반 로컬 검색 엔진(Elasticsearch + Kibana) 환경 구축
2. **Step 2**: 초기 데이터 연동 (Polling 방식 → 이후 Kafka로 전환)
3. **Step 3**: 인덱싱 및 검색 기능 검증
4. **Step 4**: 데이터 파이프라인 고도화 (Kafka/MSK 연동)
5. **Step 5**: 시각화 및 UI/서버화 (검색 UI, 검수 UI)
6. **(추가) 자연어 쿼리 파서**: Step 5 완료 후 잔여 기간에 진행한 추가 작업. 9번 섹션 참조.

## 2. 시스템 아키텍처

### 2-1. 전체 데이터 흐름 (현재 상태 기준)

```
[Qumulo (AAA1/LSD 10fps + Motional)]
        │  (지금은 수동 업로드/테스트 경로, 향후 실제 자동 적재 경로 연결 예정)
        ▼
[dev.shared.odd-tagging.input] (Kafka/MSK 토픽, 파티션 3개)
   ├─ ODD 서비스(호연)가 같은 토픽을 다른 Consumer Group으로 구독 (실제 태깅 수행)
   └─ index 서비스(우리) — group: odd-selection-consumer
        ▼
[kafka_consumer.py] (systemd: odd-kafka-consumer, 상시 구동)
   └─ kafka_message_handler.py 가 unified_pipeline.py의 함수들을 재사용
        ├─ 10fps → 1fps 다운샘플링 (정수초별 최근접 프레임 선택)
        ├─ Motional 이벤트 매칭 (±0.5초)
        └─ Bulk API로 Elasticsearch 색인
        ▼
[Elasticsearch: odd-frames-v2] (현재 976건, AAA1 488 + LSD 488)
        ▼
[검색 UI: index.html] ← server.py (systemd: odd-search-ui, 상시 구동)
        │        ├─ 체크박스 필터 검색 (기본 경로)
        │        └─ AI 자연어 검색 (/api/nlquery, 체크박스와 완전 별개 경로 — 9번 섹션 참조)
        ▼
[검수 UI: review.html] — 씬 전체 재생 + 기본 Accept/예외만 Reject 워크플로우
```

**참고**: Motional 데이터는 `motional_producer.py`가 Cron(10분 주기)으로 로컬 파일을 스캔해 같은 `odd-tagging.input` 토픽에 발행 → Consumer가 처리. ODD 서비스는 자신이 발급한 jobId와 일치하는 메시지만 처리하므로, `motional-verify-{n}` 접두사를 쓰면 우리 메시지를 무시하고 안전하게 공존 가능(호연 확인 완료).

### 2-2. 핵심 설계 결정 및 이유

| 결정                                                    | 이유                                                                                                                                                                              |

### 2-3. ODD vs Motional 데이터 구조 차이

- **ODD (AAA1, LSD, LD_General, OD_General)**: taskName별로 다른 속성 스키마, 값은 `present`/`absent`/`unknown` 3단계. AAA1은 19개 속성 + weather/time/road_type 등 촬영조건 필드 보유, LSD는 11개 속성(전부 야간 전용, 촬영조건 없음).
- **Motional**: 58개 시나리오, boolean이 아니라 실제로는 **start/end 구간(interval)** 정보로 전달됨 → 프레임 단위로 매핑. 5개 카테고리로 그룹핑됨.
- **LD_General/OD_General**: **현재도 필드 값 방식(present/absent/unknown 여부)과 실제 출력 예시가 미확인 상태**이며 **다음 담당자가 반드시 확인해야 할 항목.**

### 5-3. 우선순위 낮음 / 후순위

- 원본 영상 기반 검수 전환 (현재는 1fps 프레임 슬라이드쇼로 정상 대체 동작 중이라 급하지 않음). 영상 경로 확정 시 `review.html`의 `resolveVideoUrl()` 함수 한 곳만 수정하면 동작하도록 설계되어 있음
- 메타데이터 확장 (Meeting #4에서 언급된 "데이터센터 저장 메타 정보" — 기업/태스크/촬영일자 등 인덱싱), 아직 착수 전

## 9. 자연어 쿼리(LLM 기반) 파서 개발 — 추가 스코프

이번 스코프(1~8번 섹션)와 별개로, 태그 기반 파이프라인이 완성된 이후 잔여 기간에 자연어 검색
프로토타입을 추가로 진행하여 실제 검색 UI에 통합까지 완료했습니다. 상세 개발 기록은 Confluence
[Query Parsing] 문서에 있으며, 여기서는 다음 담당자가 알아야 할 핵심만 요약합니다.

### 9-1. 배경 및 목표

기존 태그 클릭 방식 검색과 별개로, "야간 우천 시 보행자 횡단 장면"처럼 자연어 문장을 입력하면
자동으로 검색 필터(구조화 쿼리)로 변환해주는 기능. 원래 계획(5-2 참조)에서는 "다음 단계"로만
남겨뒀으나, 회사에 계약된 LLM API가 없는 상태에서 팀원(시은)이 개인 GPU 서버에 vLLM을 띄워둔
것을 확인하여 **무료로 프로토타입 검증까지 진행**했습니다.

### 9-2. 아키텍처

> ⚠️ 아래 아키텍처는 **시은 개인 GPU 서버**에 의존하는 현재 구조입니다. 시은도 인턴이며
> Motional 데이터/vLLM 서버 담당을 다른 사람에게 인수인계할 예정이나 후임자는 아직
> 미정입니다(문서 작성 시점 기준). 자세한 내용은 0-1 섹션 경고 참고.

```
[유저] → index.html "AI 자연어 검색" 패널 (체크박스 필터와 완전 별개 UI/상태)
        → POST /api/nlquery (server.py)
        → SSH 터널(127.0.0.1:8001) → vLLM(Qwen3-VL-8B-Instruct, 시은 개인 GPU)
        → 구조화 쿼리(중첩 AND/OR) 반환
        → server.py가 그대로 검색 결과 리턴 X, index.html의 JS가 이 쿼리를
          Elasticsearch bool 쿼리로 변환(buildESQueryFromParsed()) → /api/search 재사용
        → 결과를 기존 카드 UI(renderResults())로 표시
```

- **체크박스와 완전 분리 설계**: 초기엔 파싱 결과를 체크박스 상태에 자동 반영(체크)하는 방식도
  검토했으나, taskName(AAA1/LSD) 자동 전환 필요성과 "필드 간 OR"(예: "밤이거나 비 오는")을
  체크박스로 표현할 방법이 없다는 문제로 인해 **완전히 독립된 검색 경로**로 단순화함. 자연어
  검색은 체크박스를 전혀 건드리지 않고, 곧바로 ES 쿼리로 변환해 결과만 보여줌.
- **vLLM 접속**: SSH 포트포워딩(`ssh -L 8001:127.0.0.1:8001 stradvision@10.50.10.181`)
  필요. `ui/.env`의 `VLLM_BASE_URL`이 이 로컬 포트를 가리킴. **vLLM은 systemd 미등록** — 3-4
  섹션 참조. **이건 현재의 임시 구조를 설명한 것일 뿐, 신규 환경 구축 가이드는
  [인수인계_자격증명관리] 5번 참조.**

### 9-3. 개발 과정 핵심 요약 (v1 → v18)

- **v1~v2**: 프롬프트에 규칙 텍스트만 추가하는 방식은 거의 효과 없음을 확인
- **v3**: few-shot 예시 + 출력 구조 변경(딕셔너리→조건 리스트)으로 정확도 급상승
- **임베딩 유사도 매칭 실험**(별도): `multilingual-e5-small`로 필드 설명 임베딩 매칭도 시도했으나,
  "야간에 소가 ego 차량 앞으로 지나가는 시나리오" 같은 복합 개념 쿼리에서 정답 필드가 78개 중
  65위로 밀리는 등 정확도가 낮아 **채택하지 않음** (동의어 보완용 fallback 정도로만 잠재 활용 가치)
- **v9**: taxonomy를 "형제 필드 그룹"(예: `behind_bike`/`behind_motorcycle`/`behind_long_vehicle`
  처럼 entity만 다른 필드들을 그룹으로 명시)으로 구조화 → few-shot 예시에 없던 새 조합에도 정확히
  일반화되는 것을 확인 (단, held-out 테스트에서 "동의어 표현"까지는 일반화가 불완전함을 나중에
  재확인, 9-4 참조)
- **v10**: LLM이 존재하지 않는 필드명을 지어내는 hallucination 문제 발견 → 프롬프트 규칙 +
  **코드단 검증 함수(`validate_and_sanitize()`)로 이중 방어**. 이 접근(확정적 문제는 코드로
  보장)이 이후 v18에서 다시 한번 핵심 해법으로 재사용됨.
- **v11~v14**: 속도/방향 축 동시 처리(예: "고속으로 좌회전"), LSD 태깅 자체가 야간 전용
  데이터라는 도메인 지식을 반영한 night 자동 추론, 부정 표현 중복 처리 정리, 자동 추론된
  조건에 "LSD 특성상 자동 추가" UI 배지를 붙여 투명성 확보(`auto` 플래그)
- **v15~v18**: v14의 night 자동 추론 규칙이 LSD 11개 필드 중 일부에서만 불안정하게 동작하는
  문제 발견. 원인으로 "lost in the middle"(긴 프롬프트에서 중간 내용에 대한 모델 attention
  저하) 가설을 세우고 검증했으나 부분 효과만 확인. **최종적으로 "이 규칙은 모델의 판단이
  아니라 100% 확정적인 도메인 규칙"이라는 점을 재인식하고, 프롬프트 튜닝 대신 후처리 코드
  함수(`enforce_lsd_implies_night()`)로 전환** — LSD 11개 필드 전수 테스트 100% 통과 확인.

### 9-4. 정확도 및 일반화 평가 (중요 — 반드시 읽어야 함)

- 개발 과정에서 만든 테스트 문장 기준으로는 대부분 버전이 높은 정확도를 보였으나, **개발자가
  직접 만든 예시로 검증한 수치는 진짜 일반화 성능이 아닐 수 있다는 문제의식**으로 v13 기준
  **완전히 새로운 문장 20개(held-out 테스트)**를 별도로 진행함.
- **결과: 20개 중 75% 완전정답.** 특히 "오토바이 여러 대 근처에" vs "오토바이 여러 대에
  둘러싸인"처럼 **같은 의미의 다른 표현(동의어)에 대한 일반화가 아직 불완전**하다는 구체적
  반례를 확보함. 복잡한 중첩 문장 안에서 개별 조건의 정밀도가 떨어지는 경향도 확인됨.
- **결론**: 지금 상태로도 실사용 가능한 수준이나, "100% 정확하다"고 오해하면 안 됨. 검수
  단계(review.html)에서 사람이 최종 확인하는 기존 워크플로우가 이 부정확성에 대한 안전장치
  역할을 함.

### 9-5. 다음 담당자가 이어받을 작업 (자연어 쿼리 관련, 우선순위 순)

1. **동의어 표현 일반화 개선** — 9-4에서 확인된 한계. taxonomy에 동의어 세트를 추가하거나,
   더 큰 모델(14B/32B 등)로 전환을 검토
2. **Blind held-out 테스트** — 프롬프트 내용을 모르는 다른 팀원이 직접 작성한
   문장으로 진짜 일반화 성능을 재측정 (지금까지의 20문항은 본인이 작성해 편향 가능성 있음)
3. **vLLM 운영 안정화** — 현재 systemd 미등록, 시은 개인 서버 의존. 예고 없이 꺼진 전례
   있음(3-4 섹션 참조). ⚠️ 담당자 관련 주의사항은 0-1 섹션 경고 참고.
   **[인수인계_자격증명관리] 5번의 신규 환경 구축 가이드를 참고해 이전을 최우선으로
   진행할 것을 권장**
4. **`low_streetlight_road` 필드의 auto 플래그(UI 배지) 표시 미세 오차** — 검색 결과 자체엔
   영향 없는 사소한 잔여 이슈, 우선순위 낮음
5. **복잡한 중첩 문장에서의 개별 조건 정밀도 점검 체계** — 9-4에서 확인된 패턴을 팀에 공유하고,
   복잡한 질의 결과는 검수 단계에서 한 번 더 확인하는 습관 안내 필요
