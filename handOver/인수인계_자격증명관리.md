# 자격증명(.env) 관리 인수인계

> 실제 비밀번호/키 값은 이 문서에 적지 않습니다. 각 파일의 **위치, 필요한 키 이름, 확인·재발급 방법**만 정리합니다.
> 인수인계 시점에 새 담당자 본인 계정으로 재발급하는 것을 권장합니다 (특히 AWS IAM 키, ES 비밀번호).

---

## ⚠️ [필수] hayoung.kim 계정 삭제 전 이관 체크리스트

`hayoung.kim` 계정은 **로그인 차단이 아니라 실제 삭제(userdel)될 예정**입니다.
아래 두 가지를 **먼저 이관하지 않고 계정을 삭제하면, 즉시 서비스 중단이 발생합니다.**
계정 삭제를 진행하는 분(또는 요청받는 서버 관리자)은 반드시 아래 순서대로 먼저
처리해주세요.

### 1) systemd 서비스 소유자 변경 (필수)

`odd-kafka-consumer`, `odd-search-ui` 두 서비스가 `User=hayoung.kim`으로 등록되어
있습니다. 계정이 삭제되면 두 서비스 모두 재시작 시 실행 자체가 실패해 **검색/검수 UI가
멈추고 Kafka 메시지 처리가 중단**됩니다.

```bash
# 1. 새로 발급된 팀 공용 계정 또는 후임자 계정으로 User 값 변경
sudo systemctl stop odd-kafka-consumer odd-search-ui

sudo sed -i 's/User=hayoung.kim/User=<신규계정 또는 공용계정>/' \
  /etc/systemd/system/odd-kafka-consumer.service
sudo sed -i 's/User=hayoung.kim/User=<신규계정 또는 공용계정>/' \
  /etc/systemd/system/odd-search-ui.service

sudo systemctl daemon-reload
sudo systemctl start odd-kafka-consumer odd-search-ui
sudo systemctl status odd-kafka-consumer odd-search-ui   # active (running) 확인
```

(레포의 `deploy/odd-kafka-consumer.service`, `deploy/odd-search-ui.service` 파일도
동일하게 `User=` 값을 갱신해서 커밋해두면, 다음에 서버 재구축 시에도 정확한 값이
남아있습니다.)

### 2) Motional 자동 발행 Cron 이관 (필수)

`hayoung.kim` 계정의 crontab에 아래가 등록되어 있습니다:

```
*/10 * * * * cd /home/odd-selection/kafka && .../python3 motional_producer.py ...
```

계정 삭제 시 이 crontab도 함께 삭제되어, **Motional 데이터 자동 발행이 아무 에러 없이
조용히 멈춥니다** (알아차리기 매우 어려움 — 데이터가 며칠씩 안 들어와도 로그에 아무
이상이 안 남을 수 있음).

```bash
# 1. 기존 등록 내용 확인 (계정 삭제 전에 먼저 백업)
crontab -l -u hayoung.kim > /home/odd-selection/kafka/hayoung_crontab_backup.txt

# 2. 신규 계정(또는 공용 계정)의 crontab에 동일 내용 등록
crontab -e -u <신규계정 또는 공용계정>
# 위에서 백업한 내용을 그대로 붙여넣기

# 3. 정상 등록 확인
crontab -l -u <신규계정 또는 공용계정>
```

**더 나은 대안**: 특정 개인 계정에 다시 매다는 대신, `deploy/` 폴더에 있는
systemd 서비스처럼 **systemd timer로 전환**하면 특정 개인 계정에 종속되지 않아 이런
문제가 재발하지 않습니다. 여유가 있다면 이 기회에 전환을 고려해주세요.

### 3) 위 두 가지를 완료한 뒤에만 계정 삭제 진행

```bash
sudo userdel -r hayoung.kim   # -r: 홈 디렉토리까지 함께 삭제
```

삭제 후 아래로 최종 확인:
```bash
sudo systemctl status odd-kafka-consumer odd-search-ui   # 여전히 active (running)인지
crontab -l -u <신규계정 또는 공용계정>                     # motional_producer.py 항목 있는지
cd /home/odd-selection/scripts && python3 audit_pipeline.py  # 불일치/누락 0개인지
```

### 만약 이 절차 없이 계정이 이미 삭제되어버렸다면 (복구 절차)

당황하지 않아도 됩니다. **데이터 자체는 유실되지 않았을 가능성이 높습니다** —
Kafka는 메시지를 보관 중이고(토픽 보존 기간 안이라면), Motional 원본 파일도 서버
디스크에 그대로 있고, Elasticsearch에 이미 색인된 데이터도 계정과 무관하게 보존되어
있습니다. 아래는 "복구 불가능한 사고 처리"가 아니라 "멈춰있던 파이프라인을 다시
켜는 작업"입니다.

#### 1단계 — 현재 상태 진단

```bash
# 서비스가 왜 죽었는지 확인 (아마 "user does not exist" 계열 에러)
sudo systemctl status odd-kafka-consumer
sudo systemctl status odd-search-ui

# 계정이 실제로 삭제됐는지 확인
id hayoung.kim   # "no such user"가 나오면 삭제 확정
```

#### 2단계 — 새 계정으로 서비스 재배치

인수인계_상세본.md의 3-6 "신규 담당자 계정 온보딩 체크리스트"대로 먼저 본인 계정을
발급받은 뒤:

```bash
sudo sed -i 's/User=hayoung.kim/User=<신규계정>/' \
  /etc/systemd/system/odd-kafka-consumer.service
sudo sed -i 's/User=hayoung.kim/User=<신규계정>/' \
  /etc/systemd/system/odd-search-ui.service

sudo systemctl daemon-reload
sudo systemctl start odd-kafka-consumer odd-search-ui
sudo systemctl status odd-kafka-consumer odd-search-ui   # active (running) 확인
```

`odd-kafka-consumer`가 다시 켜지면, Consumer Group(`odd-selection-consumer`)이 이전에
멈췄던 오프셋부터 **자동으로 이어서 처리**합니다 (Kafka의 기본 동작 — 메시지가 토픽
보존 기간 안에 있다면 유실 없이 따라잡힘).

#### 3단계 — Motional 자동 발행 cron 재등록

```bash
crontab -e -u <신규계정>
# */10 * * * * cd /home/odd-selection/kafka && <python경로> motional_producer.py ... 추가
```

`motional_producer.py`는 `motional_published_state.json`을 기준으로 "아직 발행 안 한
파일"만 자동으로 찾아 발행하도록 설계되어 있으므로, cron이 며칠 멈춰있었더라도 다시
켜면 밀린 파일들을 자동으로 따라잡습니다. 수동으로 파일 목록을 대조할 필요 없습니다.

#### 4단계 — 밀린 데이터 반영 확인

```bash
cd /home/odd-selection/scripts
python3 audit_pipeline.py
# "불일치/누락: 0개" 나올 때까지 몇 분 정도 걸릴 수 있음 (밀린 메시지 처리 시간)
```

#### 5단계 — Kafka 토픽 보존 기간 초과 여부 확인 (드문 경우)

계정 삭제 후 방치된 기간이 Kafka 토픽의 메시지 보존 기간(retention)보다 길었다면,
그 구간의 메시지는 실제로 유실됐을 수 있습니다. 아래로 확인:

```bash
# kafbat UI (자격증명관리 문서의 Kafka UI 접근 절차 참고)에서
# dev.shared.odd-tagging.input 토픽의 파티션별 최소/최대 오프셋과
# Consumer Group의 현재 오프셋을 비교 — 차이가 비정상적으로 크면 유실 가능성 있음
```
유실이 의심되면 인프라 담당자에게 토픽 보존 기간 설정값을 확인 요청하고, ODD 태깅
서비스 담당자(호연)에게 Motional/ODD 쪽 재발행 가능
여부를 문의하세요.

## 1. 왜 이 문서가 필요한가

프로젝트 진행 중 총 **3차례** 자격증명 관련 사고/재정비가 있었음:

1. 브라우저 JS에 ES 비밀번호가 하드코딩되어 있던 것 발견 → 백엔드 프록시로 전환
2. `scripts/*.py`에 ES 비밀번호가 코드에 직접 박혀 있던 것 뒤늦게 발견
3. Git 초기 커밋에 `elk/.env`(비밀번호 평문 포함)가 그대로 들어가 있던 것 발견 (`git rm --cached`로 추적만 해제, **히스토리에는 여전히 남아있음**)

같은 값이 여러 곳에 흩어져 있다 보니 값이 바뀌면 동기화가 깨지는 문제가 반복됐음. 인수인계 시점에 한 번에 정리하는 것이 안전함.

## 2. 자격증명 파일 전체 목록

| 파일 위치                          | 용도                                                                                                    | 필요한 키                                                                                       | Git 추적 여부                                                            |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `/home/odd-selection/elk/.env`     | Docker Compose(Elasticsearch/Kibana)가 참조                                                             | `STACK_VERSION`, `ELASTIC_PASSWORD`, `ES_MEM`, `KIBANA_PORT`, `ES_PORT`, `ES_DATA_PATH`         | ❌ (`.gitignore`) — **과거 커밋 히스토리엔 평문으로 남아있음, 3-4 참고** |
| `/home/odd-selection/ui/.env`      | 검색/검수 UI 백엔드(`server.py`) + AI 자연어 검색(vLLM 접속 정보 포함, 5번 참고)                        | `ES_USER`, `ES_PASS`, `IMAGE_ALLOWED_ROOTS`, `VLLM_BASE_URL`, `VLLM_MODEL_NAME`, `VLLM_API_KEY` | ❌                                                                       |
| `/home/odd-selection/scripts/.env` | `unified_pipeline.py`, `audit_pipeline.py` (Kafka Consumer도 이 파일들의 함수를 재사용하므로 간접 참조) | `ES_USER`, `ES_PASS`                                                                            | ❌                                                                       |
| `/home/odd-selection/kafka/.env`   | Kafka(MSK) 연결 스크립트 (`test_connection.py`, `kafka_consumer.py`, `*_producer.py`)                   | `KAFKA_BROKER`, `KAFKA_REGION`, `AWS_PROFILE`                                                   | ❌                                                                       |
| `~/.aws/credentials`               | AWS IAM 인증 (Kafka MSK 접속용)                                                                         | `[odd-msk]` profile: `aws_access_key_id`, `aws_secret_access_key`                               | 해당 없음 (프로젝트 폴더 밖, 홈 디렉토리)                                |
| `~/.aws/config`                    | AWS 리전 설정                                                                                           | `[profile odd-msk] region=ap-northeast-2`                                                       | 해당 없음                                                                |

**핵심 원칙**: `.env`는 "프로젝트 폴더 안에 두되 Git이 무시"하는 방식, `~/.aws/`는 "애초에 프로젝트 폴더 밖에 두는" 방식. 민감도가 높을수록(AWS 키 등) 프로젝트 디렉토리 자체에서 물리적으로 분리하는 원칙을 따름.

**참고**: vLLM(5번 섹션)은 이 원칙과 성격이 조금 다름 — 자체 발급하는 비밀번호가 아니라 **시은 개인 서버 접속 계정**에 의존하는 구조라서, 아래 3~4번의 "재발급" 개념이 그대로 적용되지 않음. 5번에서 별도로 다룸.

## 3. Elasticsearch 비밀번호

### 3-1. 동기화 필요한 3곳

`elk/.env`, `ui/.env`, `scripts/.env` — **이 3개 파일의 ES 비밀번호 값은 항상 동일해야 함.** 하나만 바꾸고 나머지를 안 바꾸면 인증 실패(`401 security_exception`)가 남.

### 3-2. 현재 값 확인 방법

```bash
cat /home/odd-selection/ui/.env       # ES_USER, ES_PASS 확인
curl -u elastic:<위에서_확인한_값> "http://localhost:9200/_cluster/health" -w "\n%{http_code}\n"
# → 200이 나오면 정상
```

### 3-3. 비밀번호를 모르거나 재발급하고 싶을 때 (권장)

> (현재 후임자 미정 상태 — 아래는 후임자가 확정된 이후에 그 담당자가 수행할 일입니다.
> 그 전까지 자격증명 실 값은 채림이 임시 보관합니다.)

```bash
docker exec -it odd-es /usr/share/elasticsearch/bin/elasticsearch-reset-password -u elastic
```

재발급 후 반드시 **3곳(`elk/.env`, `ui/.env`, `scripts/.env`) 전부 동일하게 업데이트** → 검증:

```bash
cd /home/odd-selection/scripts
python3 audit_pipeline.py
# → "불일치/누락: 0개" 나오면 정상 (인증까지 성공해야 이 스크립트가 돌아감)
```

`elk/.env`는 Docker Compose 재시작 시에만 반영되므로, 값을 바꿨다면:

```bash
cd /home/odd-selection/elk && docker compose restart
```

### 3-4. 과거 Git 히스토리에 남은 비밀번호 (미해결 사안)

```bash
git log --all --oneline -- "*.env"
git show <커밋해시> -- "*.env"
```

`git rm --cached`는 "앞으로 추적하지 않음"일 뿐 과거 커밋에는 값이 그대로 남아있음. **저장소가 외부에 공개되거나 접근 권한이 넓어질 경우를 대비해, 위 3-3 방식으로 비밀번호를 한 번 더 리셋해두는 것을 권장.** (히스토리 자체를 지우려면 `git filter-repo` 등이 필요하나, 이번 인턴 기간엔 미실시)

## 4. AWS / Kafka(MSK) 자격증명

### 4-1. 필요한 것

- IAM Access Key ID / Secret (영준으로부터 발급)
- 브로커 엔드포인트 주소, 리전(`ap-northeast-2`), 토픽명 — 이것도 별도로 받아야 함(키만으로는 접속 불가)

### 4-2. 위치

```
~/.aws/credentials      # [odd-msk] 프로필 (Kafka 발행/구독용)
                         # [odd-indexer] 프로필 (Kafka UI 조회 전용)
~/.aws/config            # region = ap-northeast-2
/home/odd-selection/kafka/.env   # KAFKA_BROKER, KAFKA_REGION, AWS_PROFILE
```

### 4-3. 신규 담당자가 해야 할 일

> (현재 후임자 미정 상태 — 아래는 후임자가 확정된 이후에 그 담당자가 수행할 일입니다.
> 그 전까지 자격증명 실 값은 채림이 임시 보관합니다.)

1. 영준에게 본인 명의로 새 IAM 키 발급 요청 (기존 키를 그대로 재사용하지 말 것)
2. `~/.aws/credentials`, `~/.aws/config`에 위 형식대로 등록, `chmod 600 ~/.aws/credentials`
3. 연결 테스트:
   ```bash
   cd /home/odd-selection/kafka
   source venv/bin/activate
   python3 test_connection.py
   # → "✓ 카프카 인증 성공! 토픽 15개 확인됨" 나오면 정상
   ```
4. 기존 키는 영준에게 요청해 폐기(revoke) 처리

### 4-4. Kafka UI(kafbat) 조회 전용 접근

```bash
aws configure --profile odd-indexer   # 본인 키로 재설정
aws eks update-kubeconfig --name sv-shared-dev-an2-eks-main --region ap-northeast-2 --profile odd-indexer --alias odd-indexer-dev
```

이 계정은 조회 전용(토픽 생성/삭제 Deny)이라 위험도는 낮음.

## 5. vLLM (AI 자연어 검색) — 신규 환경 구축 가이드

> ⚠️ **시은도 인턴이며, Motional 데이터/vLLM 서버 관련 담당을 다른 사람에게 인수인계할
> 예정이나 후임자는 아직 미정입니다(문서 작성 시점 기준).** 이 문서를 읽는 시점에 시은이
> 이미 퇴사했거나 담당이 바뀌었을 수 있으니, 시은에게 직접 연락하기 전에 먼저 인프라
> 담당자에게 "Motional 데이터 및 vLLM 서버를 지금 누가 담당하는지"
> 확인할 것을 권장합니다.

> (추가로, 이 프로젝트 자체의 후임자도 현재 미정 상태입니다 — 아래는 후임자가 확정된
> 이후에 그 담당자가 수행할 일입니다. 그 전까지 자격증명 실 값은 채림이 임시 보관합니다.)

AI 자연어 검색 기능(`/api/nlquery`)은 현재 **시은 개인 GPU 서버**에서 돌아가는 vLLM을 빌려
쓰는 구조. 시은도 인턴이라 이 서버를 계속 쓸 수 있다는 보장이 없으므로, **다음 담당자는
가능하면 별도의 안정적인 GPU 환경으로 이전하는 것을 권장.** 아래는 "어디에 새로 만들지"
선택지와, 정해지면 바로 따라 할 수 있는 설치 절차를 정리한 것.

### 5-1. 환경 선택지 (다음 담당자가 상황에 맞게 판단)

| 선택지                                     | 장점                                                                                                        | 확인 필요한 것                                                                                              |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **A. strad35 서버 자체**                   | 이미 접근 권한 있음, 별도 서버 협의 불필요                                                                  | GPU가 실제로 있는지 미확인 — `nvidia-smi`로 먼저 확인 필요 (현재까지는 이 프로젝트 용도로 GPU를 쓴 적 없음) |
| **B. 회사 공용 GPU 인프라**                | Kafka UI 접속에 쓰던 `sv-shared-dev-an2-eks-main` 클러스터처럼, 회사가 이미 관리 중인 인프라가 있을 수 있음 | "LLM 추론용 GPU 인스턴스/파드를 배정받을 수 있는지" 문의 필요. 있다면 가장 안정적인 선택                    |
| **C. 새 개인/팀 GPU 서버**                 | 자유도 높음                                                                                                 | 신규 서버 프로비저닝 자체가 별도 승인/시간이 필요할 수 있음                                                 |
| **D. (임시) 다른 팀원 서버를 계속 빌리기** | 당장 추가 작업 없음                                                                                         | 시은과 같은 문제(예고 없는 중단, 소유권 불명확)가 반복될 위험 — 장기적으로 권장하지 않음                    |

**판단 기준**: 이 기능이 "있으면 좋은 실험적 기능"인지 "실제로 팀이 매일 쓰는 핵심 기능"인지에
따라 우선순위가 달라짐. 후자라면 B(회사 공용 인프라)를 최우선으로 알아보는 것을 권장 — 이번
인턴 기간엔 시간 제약으로 개인 서버를 빌려 썼지만, 정식 운영에는 적합하지 않음.

### 5-2. GPU 사양 확인 (선택지 정하기 전에)

Qwen3-VL-8B-Instruct(현재 쓰던 모델) 기준, 최소 **VRAM 16~24GB** 권장(양자화 여부에 따라
달라짐). 후보 서버에서 먼저 확인:

```bash
nvidia-smi
# GPU 모델명, 총 VRAM, 현재 사용 중인 프로세스/여유 메모리 확인
```

다른 프로세스가 이미 GPU를 많이 점유하고 있다면(공용 서버라면 흔함), 여유 메모리를 보고
vLLM의 `--gpu-memory-utilization` 옵션으로 사용량을 제한해야 할 수 있음.

### 5-3. vLLM 설치 및 실행 (환경이 정해진 뒤)

```bash
# 1) 가상환경 준비 (권장 — 기존 scripts/kafka venv와 분리)
python3 -m venv ~/vllm-env
source ~/vllm-env/bin/activate

# 2) vLLM 설치
pip install vllm

# 3) 서버 실행 (백그라운드 테스트용, 정식 운영은 5-4의 systemd 등록 참고)
vllm serve Qwen/Qwen3-VL-8B-Instruct --port 8001 --gpu-memory-utilization 0.8
# 최초 실행 시 HuggingFace에서 모델 가중치를 다운로드하므로 시간이 걸림 (수 GB~십수 GB)
# 인터넷 접근이 막힌 서버라면 사전에 모델을 다운로드해서 옮겨야 할 수 있음

# 4) 정상 기동 확인 (같은 서버 또는 SSH 터널 연결 후)
curl http://127.0.0.1:8001/v1/models
# → 모델 이름이 포함된 JSON 응답 오면 정상
```

다른 모델로 바꾸고 싶다면 `Qwen/Qwen3-VL-8B-Instruct` 자리에 원하는 HuggingFace 모델
ID를 넣으면 됨 (예: 더 큰 모델로 정확도 개선을 시도하려면 `Qwen/Qwen2.5-14B-Instruct` 등 —
9-5 섹션에서 언급된 "동의어 일반화 개선" 방향과 연결되는 부분).

### 5-4. systemd 등록 (정식 운영 시 필수 권장)

지금까지 겪은 문제(예고 없는 중단, 수동 관리)를 반복하지 않으려면 `odd-search-ui`와 동일한
방식으로 systemd에 등록하는 것을 권장:

```ini
# /etc/systemd/system/odd-vllm.service (예시, 경로/가상환경 경로는 실제 환경에 맞게 수정)
[Unit]
Description=vLLM Server for ODD AI Search
After=network.target

[Service]
User=<실행계정>
WorkingDirectory=/home/odd-selection
ExecStart=/home/<계정>/vllm-env/bin/vllm serve Qwen/Qwen3-VL-8B-Instruct --port 8001 --gpu-memory-utilization 0.8
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now odd-vllm
sudo systemctl status odd-vllm
```

### 5-5. `ui/.env` 값 업데이트

새 환경 주소에 맞게 아래 값을 갱신:

```
VLLM_BASE_URL=http://127.0.0.1:8001/v1     # 같은 서버(strad35)에 vLLM을 올렸다면 그대로,
                                             # 다른 서버라면 그 서버의 접속 방식에 맞게 조정
                                             # (SSH 터널을 계속 쓴다면 로컬 포트를 그대로 유지)
VLLM_MODEL_NAME=Qwen/Qwen3-VL-8B-Instruct   # 5-3에서 실행한 모델명과 정확히 일치해야 함
VLLM_API_KEY=dummy                          # vllm serve에 --api-key를 안 걸었다면 임의 문자열 유지,
                                             # 걸었다면 그 키 값으로 교체
```

값 변경 후 반드시 재시작:

```bash
sudo systemctl restart odd-search-ui
```

## 6. 이미지 서빙 경로 제한 (`IMAGE_ALLOWED_ROOTS`)

비밀번호는 아니지만 보안 설정값이라 함께 정리. `ui/.env`에 정의:

```
IMAGE_ALLOWED_ROOTS=/mnt/data-center/scenes:/mnt/data-center/raw-datas
```

- 콜론(`:`)으로 여러 경로 지정 가능
- 프레임 이미지가 **심볼릭 링크**인 경우, 링크가 가리키는 실제 경로(`realpath` 기준)도 이 목록에 포함되어야 함 — 안 그러면 정상 이미지까지 403으로 차단됨
- 검증:
  ```bash
  curl -i "http://localhost:8080/api/image?path=/etc/passwd"
  # → 403 Forbidden 이어야 정상
  ```
